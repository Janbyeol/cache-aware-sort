# Cache-Aware Hybrid Sort Study (64B Cache-Line Optimization)

[English](README.md) | **한국어**

작은 블록의 정렬, 병합 경계 축소, 타일 단위 병합을 실험하는 C++20 프로젝트입니다. 게임에서 착안한 합성 워크로드를 사용해 네 가지 정렬 변형을 `std::sort`, `std::stable_sort`, 기본 퀵 정렬과 비교합니다.

실험 대상은 **4바이트 정수 키**와 **8바이트 키 + 엔티티 ID 레코드**입니다. 입력에 따라 성능이 달라지는 학습 프로젝트이며, 표준 라이브러리를 대체하는 범용 정렬 라이브러리를 목표로 하지는 않습니다.

> **AI 활용 안내**
>
> 저는 알고리즘과 컴퓨터 구조를 공부하는 학부생입니다. C++20 코드 구현, 저수준 최적화 탐색, 벤치마크·프로파일링 도구 작성에는 ChatGPT와 Gemini를 적극적으로 활용했습니다. 처음 세운 가설은 정렬을 공부하며 생긴 제 의문에서 출발했습니다. 이는 프로젝트를 시작한 과정을 설명하는 것이며, 사용한 기법 자체가 새로운 발명이라는 뜻은 아닙니다.

## 시작하게 된 계기

정렬 알고리즘을 공부하다가 이런 의문이 들었습니다. *퀵 정렬은 최악의 경우 O(N²)이고, 평균 시간 복잡도도 힙 정렬이나 병합 정렬과 같은 O(N log N)인데 왜 실제로는 더 빠를 수 있을까?*

실제 성능에는 메모리 접근 패턴, 비교와 이동 비용, 분기 동작, 구현 방식이 함께 영향을 줍니다. 여기서 두 가지 질문으로 이어졌습니다.

1. **64바이트 크기의 작은 구간**에서 삽입 정렬로 전환하면 분할을 계속하는 비용을 줄일 수 있을까?
2. 분할 구간의 통계나 병합 경계에서 바깥쪽으로 탐색하는 방법으로 불필요한 작업을 줄일 수 있을까?

현재 구현은 리프 크기를 64바이트, 타일 크기를 8 KiB로 고정합니다. 따라서 리프에는 `int32_t` 키 16개 또는 레코드 8개가 들어갑니다. 이는 튜닝 값일 뿐입니다. 크기가 64바이트라고 해서 해당 구간이 캐시 라인에 정렬되거나, 항상 L1에 상주하거나, 캐시 적중이 보장되는 것은 아닙니다.

## 빌드와 실행

### Linux / GCC

C++20을 지원하는 `g++`, GNU Make, 셸이 필요합니다. 저장소 루트에서 실행합니다.

```bash
git clone https://github.com/Janbyeol/cache-aware-sort.git
cd cache-aware-sort

# 두 자료형의 정확성 테스트를 빌드하고 실행합니다.
make -f makefile.txt test

# 테스트와 벤치마크 실행 파일 네 개를 모두 빌드합니다.
make -f makefile.txt all

# 두 자료형의 실제 경과 시간 벤치마크를 실행합니다.
make -f makefile.txt bench
```

파일 이름이 **`makefile.txt`**이므로 `-f` 옵션이 필요합니다. 기본 플래그는 `-O3 -march=native -std=c++20 -Wall -Wextra -Iinclude`입니다. `-march=native`로 빌드한 실행 파일은 다른 CPU에서 실행되지 않을 수 있습니다.

- `test_4b` / `test_8b`: 정확성 테스트입니다. 현재 테스트는 **자료형마다 3,372개 검증**을 수행합니다. 경계 크기, 일곱 워크로드, 무작위 입력, 레코드 무결성, 할당 크기 오버플로, 경계 축소 병합의 추가 회귀 테스트를 포함합니다.
- `bench_4b` / `bench_8b`: 정해진 크기들을 측정하는 경과 시간 벤치마크입니다. 작업 디렉터리에 `key_only_4b_summary.csv`, `key_id_8b_summary.csv`를 저장합니다.
- `make -f makefile.txt bench`는 특정 크기 하나가 아니라 전체 벤치마크를 실행합니다. `N`을 직접 지정하려면 아래의 플랫폼별 프로파일링 스크립트를 사용합니다.

### Windows / Visual Studio

Visual Studio C++ 빌드 도구와 Windows SDK를 설치한 환경에서 실행합니다.

```powershell
.\generate_solution.bat
```

생성된 `cache-aware-sort.sln`을 열고 **Release | x64**를 선택해 빌드합니다. 솔루션에는 `test_4b`, `test_8b`, `bench_4b`, `bench_8b`가 있으며, 실행 파일은 `bin\Release\`에 생성됩니다.

```powershell
.\bin\Release\test_4b.exe
.\bin\Release\test_8b.exe
```

생성되는 Release 프로젝트는 AVX2를 사용하므로 이를 지원하는 x64 환경이 필요합니다. 이 솔루션 생성기는 **네이티브 ARM64 빌드용이 아닙니다**. Windows ARM64 프로파일링에는 아래의 별도 스크립트를 사용합니다.

## 네 가지 아이디어의 발전 과정

각 구현은 [`include/hybrid_sorts.hpp`](include/hybrid_sorts.hpp)의 자료형과 공통 저수준 함수를 사용합니다.

### Idea 1: 캐시 라인 크기의 퀵 정렬 리프

[`cache_leaf_quick`](src/idea1_cache_leaf_quick.cpp)은 세 후보의 중앙값으로 피벗을 선택하고 Hoare 방식으로 분할합니다. 분할 구간이 64바이트 이하가 되면 삽입 정렬로 전환합니다. 같은 분할 함수를 사용하면서 원소 하나까지 재귀 호출을 계속하는 `pure_quick` 기준 구현과 비교해, 작은 구간에서 분할을 멈추는 효과를 살펴봅니다.

이 기준은 작은 구간의 분할 작업을 줄이지만, 데이터에 따라 달라지는 분기나 퀵 정렬의 최악 시간 복잡도까지 없애지는 않습니다.

### Idea 2: 평균값을 이용한 다음 피벗 선택

[`mean_pivot_quick`](src/idea2_mean_pivot_quick.cpp)은 Hoare 분할을 수행한 뒤 **양쪽 구간을 다시 순회**해 합계와 최솟값·최댓값을 구합니다. 이 통계로 다음 피벗을 평균값에 가깝게 선택하고, 모든 키가 같은 구간은 건너뜁니다.

현재 구현은 분할과 통계 수집을 한 번의 순회로 처리하지 않습니다. 추가 순회 비용도 함께 고려해야 합니다. 특히 음수 키의 정수 나눗셈 때문에 평균이 최댓값과 같아지는 경우에도 분할이 진행되도록 피벗 범위를 제한합니다.

### Idea 3: 경계 구간을 줄이는 상향식 병합

[`boundary_trimmed_merge`](src/idea3_boundary_trimmed_merge.cpp)는 하향식 분할 대신 상향식 병합에서 출발합니다.

1. 64바이트 리프를 삽입 정렬합니다.
2. 각 8 KiB 타일 안에서 초기 병합 단계를 마칩니다.
3. 인접한 두 정렬 구간의 경계가 이미 올바른 순서라면 병합을 건너뜁니다.
4. 그렇지 않으면 경계에서 양쪽 바깥으로 탐색해 실제로 겹치는 가운데 구간을 찾습니다. 짧은 선형 탐색 뒤에 경계 검사, 지수 탐색, 이진 탐색을 사용합니다.
5. 겹치는 구간이 작거나 양쪽 크기 차이가 크면 작은 쪽만 보조 버퍼에 복사하고 원본에 직접 병합합니다. 양쪽이 크고 균형적이면 양방향 병합으로 보조 버퍼에 쓴 뒤 원본으로 복사합니다.

저장된 결과에서는 뒤에 새 데이터가 추가되는 입력과 프레임 흔들림 입력에서 이 방향이 특히 유용했습니다. 반대로 성능이 크게 나빠지는 입력도 있으며, 아래 결과에 함께 정리했습니다.

### Idea 4: 타일 단위 핑퐁 병합

[`tiled_pingpong_merge`](src/idea4_tiled_pingpong_merge.cpp)도 8 KiB 타일을 사용하지만, 병합 단계마다 읽기 버퍼와 쓰기 버퍼의 역할을 교환합니다. 이진 탐색으로 겹치는 구간을 줄이고, 이미 정렬된 바깥 구간도 다음 단계에서 필요하면 목적지 버퍼로 복사합니다.

배열 전체의 정렬 방향을 일부 표본으로 살피고, 대부분 내림차순인 입력을 조정하는 처리도 있습니다. 조기 종료 전에는 전체 배열이 실제로 정렬되었는지 확인하므로, 표본만으로 정렬 완료를 판단하지 않습니다.

두 병합 구현의 핵심 루프에는 조건부 선택이 사용됩니다. 이러한 루프, 경계 탐색, 타일링 구현에는 AI의 도움을 받았습니다. 실제로 `cmov`, 조건부 선택 명령, 분기 중 무엇이 생성되는지는 컴파일러와 대상 CPU에 따라 다르며, 알고리즘 전체에서 분기가 사라지는 것은 아닙니다.

## 워크로드

모든 입력은 [`generate_game_workload`](src/benchmark_api.cpp)로 생성합니다. 실제 게임 엔진에서 수집한 데이터가 아니라 합성 워크로드입니다.

| ID | 워크로드 | 생성 방식 |
| --- | --- | --- |
| 0 | 무작위 3D 거리 | 의사 난수 3D 좌표에서 거리의 제곱을 계산합니다. 프로파일러의 기존 이름은 `0_Uniform_Random`이지만, **계산된 거리 키는 균등분포가 아닙니다**. |
| 1 | 프레임 흔들림 | 점들을 거리순으로 정렬한 뒤 좌표를 조금 움직이고 거리 키를 다시 계산합니다. |
| 2 | 뒤에 5% 추가 | 정렬된 앞부분 뒤에 `floor(N / 20)`개의 정렬되지 않은 새 키를 둡니다. |
| 3 | 거리 버킷 | 거리 키를 1,000,000으로 나누어 약 300개 버킷과 다수의 중복 키를 만듭니다. |
| 4 | 대부분 내림차순 | 내림차순 키에 약 1%의 무작위 인접 교환을 적용합니다. |
| 5 | 가우시안 유사 | 의사 난수 정수 네 개를 더해 종 모양 분포를 만듭니다. 정확한 정규분포는 아닙니다. |
| 6 | 오르간 파이프 | 정렬된 키를 앞에서는 증가하고 뒤에서는 감소하는 산 모양으로 배치합니다. |

## 저장된 실험 결과

저장소의 [Linux CSV](docs/linux/)에는 **하드웨어 카운터**가 기록되어 있으며, 실제 경과 시간은 없습니다. 아래 표는 [`N = 1,000,000` CSV](docs/linux/pure_cache_results_N=1000000.csv)의 **4바이트 정수 키** 결과입니다. 현재 코드를 새로 실행한 결과가 아니라 저장된 측정값을 정리한 것입니다.

CSV에는 측정 당시 CPU 모델, 컴파일러와 버전, 운영체제 정보, 정확한 빌드 리비전, 개별 반복 측정값이 포함되어 있지 않습니다. 따라서 다른 환경에서도 같은 성능을 보장하거나 완전히 재현 가능한 기록으로 보기는 어렵습니다. 이전 README의 밀리초 수치는 저장된 CSV로 확인할 수 없어 제외했습니다.

### 일곱 시나리오의 사이클 수

`M`은 백만 사이클입니다. 괄호 안은 `std::sort 사이클 / 해당 알고리즘 사이클`입니다. 1보다 크면 `std::sort`보다 기록된 사이클이 적다는 뜻이며, **실제 경과 시간도 같은 비율로 빨라졌다는 뜻은 아닙니다**.

| 워크로드 | `std::sort` | `std::stable_sort` | 경계 축소 병합 | 타일 핑퐁 병합 |
| --- | ---: | ---: | ---: | ---: |
| 무작위 3D 거리 | 230.79M | 278.63M | 142.74M (1.62×) | 139.40M (1.66×) |
| 프레임 흔들림 | 137.26M | 150.98M | 90.97M (1.51×) | 97.25M (1.41×) |
| 뒤에 5% 추가 | 85.48M | 38.75M | 24.66M (3.47×) | 28.76M (2.97×) |
| 거리 버킷 | 114.67M | 164.06M | 142.81M (0.80×) | 139.54M (0.82×) |
| 대부분 내림차순 | 23.68M | 40.15M | 110.38M (0.21×) | 17.14M (1.38×) |
| 가우시안 유사 | 207.85M | 259.24M | 142.79M (1.46×) | 139.30M (1.49×) |
| 오르간 파이프 | 246.65M | 34.95M | 61.74M (3.99×) | 61.05M (4.04×) |

불리한 결과도 중요합니다. 중복 키가 많은 거리 버킷에서는 두 병합 구현 모두 `std::sort`보다 많은 사이클을 사용합니다. 대부분 내림차순인 입력에서는 경계 축소 병합이 약 **4.66배의 사이클**을 사용합니다. 오르간 파이프에서는 `std::stable_sort`가 두 구현보다 낫습니다. 모든 워크로드에서 이기는 알고리즘은 없습니다.

### 캐시와 분기 카운터가 보여 주는 차이

위의 무작위 3D 거리 워크로드를 자세히 보면 다음과 같습니다.

| 알고리즘 | IPC | L1D 읽기 적중률 | L1D 읽기 미스 수 | 분기 예측 적중률 |
| --- | ---: | ---: | ---: | ---: |
| `std::sort` | 0.63 | 97.83% | 662,145 | 75.54% |
| `boundary_trimmed_merge` | 2.19 | 95.11% | 2,020,305 | 95.02% |
| `tiled_pingpong_merge` | 2.21 | 96.93% | 1,256,029 | 94.89% |

두 병합 구현은 사이클이 적고 IPC와 분기 예측 적중률이 높지만, **L1D 읽기 미스는 더 많고 읽기 적중률은 낮습니다**. 이 결과만으로 캐시 동작 개선이 사이클 감소의 원인이라고 단정할 수 없습니다. 알고리즘마다 접근 횟수라는 분모도 다르므로, 비율과 절대 횟수를 함께 봐야 합니다.

저장된 CSV 열 개는 두 자료형에 대해 `N = 16, 64, 256, 1024, 2048, 8192, 32768, 262144, 1000000, 5000000`을 다룹니다. 8바이트 레코드와 다른 크기는 별도로 평가해야 합니다. 예를 들어 원소 백만 개의 대부분 내림차순 입력에서 8바이트 핑퐁 병합은 `std::sort`보다 약 16.3% 많은 사이클을 사용해, 위의 4바이트 결과와 다릅니다. [`docs/windowsARM/`](docs/windowsARM/)에는 현재 자리표시자만 있으며 공개된 측정 결과는 없습니다.

## 벤치마크 방법과 재현

### 실제 경과 시간 측정

`make -f makefile.txt bench`는 일곱 알고리즘, 일곱 시나리오, 다섯 크기(`128, 2048, 8192, 131072, 1000000`)를 실행합니다. 배열당 측정값 다섯 개의 중앙값을 사용하며, 작은 배열은 여러 개를 묶어 타이머 오버헤드를 줄입니다. 입력 생성, 정렬 전 복사, 결과 검증은 측정 구간 밖에 있습니다. 정렬 함수 안에서 수행하는 보조 버퍼 할당과 내부 복사 등은 포함됩니다.

각 측정 뒤에 정렬된 키를 검증하고, 8바이트 모드에서는 레코드 ID와 페이로드의 무결성도 확인합니다. 출력의 `trimmed_merge`는 `boundary_trimmed_merge_sort`를 가리킵니다.

### Linux 하드웨어 카운터

GCC, Bash, 그리고 호스트에서 이미 허용된 하드웨어 성능 카운터 접근 권한이 필요합니다. 순수 정렬 프로파일러는 `perf_event_open`을 직접 호출합니다. 별도의 `run_perf_csv.sh`는 프로세스 전체를 `perf stat`으로 감싸므로 측정 범위가 다릅니다.

```bash
# 한 가지 크기, 세 번 반복, 4B와 8B 모두 측정합니다.
bash utility/linux/run_pure_perf.sh 1000000 3 results.csv

# 열 가지 크기, 세 번 반복, 크기 사이에 5초 대기합니다.
# 저장소의 기존 측정값을 보존하도록 별도 디렉터리를 사용합니다.
bash utility/linux/run_pure_perf.sh --all 3 5 results/linux
```

스크립트가 프로파일링 실행 파일을 빌드하고 CSV와 Markdown 요약을 저장합니다. 전체 크기를 실행하면 통합 파일인 `pure_cache_results_all.csv`도 생성합니다.

순수 정렬 프로파일러는 시드 `42`로 만든 입력을 재사용하고, 매번 측정 전에 원본을 복사합니다. 카운터를 두 번의 별도 정렬 실행으로 나누어 수집한 뒤 반복 횟수의 산술평균을 계산합니다. 입력 생성과 정렬 전 복사는 제외하지만, 정렬 내부의 할당·복사와 일부 카운터 제어 오버헤드는 포함합니다. 복사가 캐시 상태에 영향을 주므로 통제된 콜드 캐시 실험은 아닙니다. 경과 시간 측정 도구와 달리 **결과 검증을 수행하지 않으므로** 먼저 정확성 테스트를 실행해야 합니다.

카운터 지원과 접근 권한은 CPU, 커널, 가상 머신, 컨테이너에 따라 다릅니다. 사이클·명령어 카운터를 열지 못하면 실행이 중단되지만, 나머지 카운터가 지원되지 않으면 0으로 기록되거나 오해하기 쉬운 100% 적중률이 표시될 수 있습니다. 해석 전에 카운터 지원 여부를 확인해야 합니다. 이벤트는 개별적으로 활성화되며 다중화와 보정이 적용될 수 있으므로, 짧은 실행과 서로 다른 이벤트의 비율은 특히 주의해야 합니다. `LLC`로 표시되는 일반 캐시 이벤트의 의미도 CPU마다 다를 수 있습니다. Linux 순수 정렬 프로파일러 자체는 CPU affinity를 고정하지 않습니다.

접근이 거부되면 적절한 PMU 접근 권한이 있는 환경을 사용하거나 관리자에게 확인하세요. 시스템 전체의 보안 설정을 바꾸는 것이 항상 필요하거나 적절한 것은 아닙니다. 스크립트 사용법은 [Linux 프로파일링 가이드](utility/linux/LINUX_PERF_GUIDE.md)를 참고하세요.

### Windows ARM64 사이클과 시간 측정

Windows 프로파일러는 `QueryPerformanceCounter`로 경과 시간을, `QueryThreadCycleTime`으로 스레드 사이클을 측정합니다. 이는 **Linux의 L1D·LLC·분기 카운터가 아니므로** 같은 지표처럼 비교하면 안 됩니다. 워밍업, 작은 입력의 배치 실행, 중앙값 집계 방식도 Linux 순수 정렬 프로파일러와 다릅니다.

```powershell
# 한 가지 크기, 세 번 반복, 두 자료형을 측정합니다.
.\utility\windowsARM\run_pure_perf.bat 1000000 3 results.csv

# 전체 크기를 별도 디렉터리에 저장합니다.
.\utility\windowsARM\run_pure_perf.bat --all 3 5 results\windowsARM
```

스크립트는 Visual Studio 컴파일러를 우선 사용하고 ARM64 호스트에서는 ARM64를 선택합니다. 이후 Clang/GCC 대체 경로를 사용합니다. 필요한 C++ 도구와 SDK를 설치하고, 모든 대체 경로가 네이티브 ARM64를 생성한다고 가정하지 말고 출력된 아키텍처를 확인하세요. 자세한 사용법은 [Windows ARM64 가이드](utility/windowsARM/WINDOWS_ARM_GUIDE.md)에 있습니다.

새 결과를 공유할 때는 커밋 SHA, CPU·캐시 구성, 운영체제, 컴파일러·표준 라이브러리 버전, 플래그, affinity·전원 설정, 카운터 지원 여부, 자료형, `N`, 워크로드, 시드, 반복 측정값을 함께 남기는 것이 좋습니다. 경과 시간과 하드웨어 카운터 실행 결과는 구분해서 기록하세요.

## 적용 범위와 한계

- **API:** 함수는 `hsort::Item*`와 원소 개수를 받아 부호 있는 32비트 키 기준 오름차순으로 정렬합니다. 기본 `int32_t`와 `-DBENCH_RECORD=1`로 선택하는 `DistanceRecord { key, entity_id }`를 지원합니다. 범용 반복자나 사용자 정의 비교 함수 인터페이스는 없습니다.
- **메모리:** 리프보다 큰 입력에서 경계 축소 병합은 원소 `N`개 분량의 보조 버퍼를 할당합니다. 핑퐁 병합도 전체 정렬 방향을 확인하는 빠른 경로에서 끝나지 않으면 같은 크기의 버퍼를 할당합니다. 작은 쪽만 복사하는 병합은 일부 겹침 구간의 복사량을 줄일 뿐, 할당 용량을 줄이지는 않습니다. 할당은 실패할 수 있습니다.
- **복잡도:** 두 병합 구현은 최악 O(N log N)의 작업과 O(N)의 추가 공간을 사용합니다. 사용자 정의 퀵 정렬 구현에는 introsort와 같은 대체 경로가 없으므로 불리한 입력에서 O(N²)의 작업이 발생할 수 있습니다.
- **안정성:** 경계 축소 병합은 같은 키의 순서를 보존하며, `std::stable_sort`와 비교하는 전용 8바이트 레코드 회귀 테스트가 있습니다. 사용자 정의 퀵 정렬들은 불안정 정렬입니다. 핑퐁 병합 역시 전체 내림차순 입력을 조정하는 과정에서 같은 키의 레코드 순서가 바뀔 수 있어 **안정 정렬을 보장하지 않습니다**.
- **이식성:** 64바이트와 8 KiB는 하드웨어에서 감지한 값이 아니라 고정 상수입니다. 생성되는 명령어와 성능은 CPU, 컴파일러, 플래그, 표준 라이브러리 구현, 입력에 따라 달라집니다.
- **검증 범위:** 합성 워크로드와 테스트 통과만으로 실서비스 사용 준비가 끝났다고 볼 수 없습니다. 임의의 비교 함수, 더 큰 레코드, 병렬 정렬, 모든 적대적 입력을 다루지는 않습니다.

이번 실험에서 얻은 결론은 이미 정렬된 부분이 많은 입력에서는 병합 경계를 줄이는 접근을 더 살펴볼 만하고, 핑퐁 병합은 복사 비용에 대해 다른 선택지를 제공한다는 것입니다. 캐시 크기에 맞춘 블록이 언제나 정렬을 빠르게 만든다고 가정하기보다, 실제로 사용할 입력에서 유리한 경우와 불리한 경우를 함께 측정하고 설명하는 것이 다음 단계라고 생각합니다.
